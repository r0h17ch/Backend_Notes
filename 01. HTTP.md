## 1. Core Foundations of HTTP

### The 90% Focus Principle
Backend engineering is a vast domain spanning hundreds of protocols and specialized tools. Trying to learn every esoteric protocol at once leads to analysis paralysis. In practice, roughly **90% of production codebases** rely on **HTTP** as the primary medium through which clients (browsers, mobile apps, third-party consumers) and servers exchange data. Mastering HTTP from first principles provides the foundation required to understand every higher-level web framework.

### Pillar 1: Statelessness
At the core of HTTP is the rule that the protocol is **stateless**:
* **Zero Memory of Past Interactions:** The server retains no context or historical memory of previous requests. Once the server processes a request and transmits the response, the connection context is effectively forgotten. If the exact same client dispatches a second request a millisecond later, the server treats it as a completely new, isolated event.
* **Self-Contained Requests:** Because the server remembers nothing, **every individual HTTP request must be 100% self-contained**. It must package all metadata, routing paths, action methods, and security credentials (e.g., authorization headers, session cookies, bearer tokens) necessary for the server to authenticate and satisfy that specific transaction.
* **Architectural Benefits:**
  1. *Simplicity:* Server implementations do not need complex session-tracking state machines or dedicated in-memory tracking logic just to handle basic communication.
  2. *Horizontal Scalability:* Incoming requests can be routed across an arbitrary pool of stateless server instances behind a load balancer without requiring sticky sessions. Any node in the fleet can process any request.
  3. *Crash Resilience:* If an individual server node crashes mid-stream, client interaction state is not lost or corrupted because the server was never storing that state in its local process memory.
* **Managing State over a Stateless Protocol:** While raw HTTP is stateless, modern web applications require continuity (user logins, shopping carts, checkout workflows). Developers achieve statefulness by layering state management abstractions (sessions, cookies, JWTs) on top of HTTP.

### Pillar 2: Client-Server Model
Communication in HTTP strictly follows an asymmetric client-server relationship:
* **The Client:** Always acts as the **initiator**. The client builds the request (specifying URI, method, headers, and body) and establishes the network connection.
* **The Server:** Acts as a passive listener hosting resources (APIs, static files, databases). It waits for incoming connections, processes incoming data, executes business logic, and returns a response (HTML, JSON, binary streams, or error definitions).
* **Unidirectional Initiation:** Under standard HTTP, the server cannot initiate an outbound transmission to an arbitrary client without a prior client-initiated request.

### HTTP vs. HTTPS
At the application layer, **HTTP and HTTPS are architecturally identical**. They utilize the same methods, header syntax, status codes, and URI path conventions. HTTPS simply wraps standard plain-text HTTP messages inside a cryptographic security layer (**TLS - Transport Layer Security**), ensuring data encryption, integrity, and server authentication in transit.

## 2. Transport Layer, OSI Model & Protocol Evolution

### Underlying Transport (TCP vs. UDP)
* HTTP does not strictly require a connection-oriented transport protocol; its formal requirement is simply a **reliable transport layer** that guarantees ordered message delivery without silent packet loss (or raises an explicit error if a drop occurs).
* Between the internet's two dominant transport protocols:
  * **UDP (User Datagram Protocol):** Connectionless and unreliable (packets may arrive out of order or drop silently).
  * **TCP (Transmission Control Protocol):** Connection-oriented and highly reliable, establishing connections via a **3-way handshake** (`SYN` $\rightarrow$ `SYN-ACK` $\rightarrow$ `ACK`) with built-in retransmissions and sequence ordering.
* Consequently, HTTP/1.0, HTTP/1.1, and HTTP/2 rely directly on **TCP**.

### The OSI Model Perspective
* Backend software engineers work predominantly at **Layer 7 (Application Layer)** of the OSI 7-layer stack.
* While lower layers handle IP packet routing (Network Layer) and byte segmentation/handshakes (Transport Layer), Layer 7 dictates the business semantics of the data. 

### Evolution of HTTP Specifications

| HTTP Version | Transport Protocol | Core Architectural Changes & Engineering Trade-offs |
| :--- | :--- | :--- |
| **HTTP/1.0** | TCP | Opens and terminates a **brand-new TCP connection for every single request/response cycle**. This causes severe latency overhead due to repeated 3-way handshakes and slow-start congestion mechanics. |
| **HTTP/1.1** | TCP | Introduced **Persistent Connections (`Connection: keep-alive`)** by default, allowing multiple sequential requests over a single established TCP stream. Added **Chunked Transfer Encoding** and standardized cache validation. Suffered from **HTTP Head-of-Line (HoL) blocking** (requests had to be queued and completed sequentially on the connection). |
| **HTTP/2.0** | TCP | Replaced plain-text transmission with **Binary Framing**. Introduced **Multiplexing** (concurrent bidirectional streams interleaved over a single TCP connection), **HPACK Header Compression**, and **Server Push**. While application-level HoL blocking was solved, it remained vulnerable to **TCP-level HoL blocking** (a single dropped TCP packet stalls all multiplexed streams). |
| **HTTP/3.0** | **QUIC (over UDP)** | Completely redesigned transport by replacing TCP with **QUIC running over UDP**. Provides zero-RTT connection resumption, independent streams that eliminate TCP Head-of-Line blocking during packet loss, and robust connection migration across changing client IP addresses. |

## 3. Anatomy of HTTP Messages

Every HTTP transaction consists of a plain-text (or framed binary) message categorized into either a Request or a Response.

### The Request Message Structure
Sent from the client to the server:
1. **Start Line (Request Line):**
   * *Method:* Identifies the action verb (e.g., `POST`, `GET`).
   * *Target URI/Path:* The resource being addressed (e.g., `/api/v1/users`).
   * *Protocol Version:* Declares client protocol support (e.g., `HTTP/1.1`).
2. **Host Header:** Mandatory in HTTP/1.1; specifies the target domain name and optional port.
3. **Request Headers:** A series of key-value pairs separated by colons defining metadata.
4. **Blank Line:** A mandatory CRLF (`\r\n`) delimiter signaling the absolute end of the header section.
5. **Request Payload / Body:** The raw serialized data payload (JSON, form bytes, XML) sent to the server.

```http
POST /api/v1/users HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json
Content-Length: 38

{"name": "Alice", "role": "engineer"}
```

### The Response Message Structure
Sent from the server back to the client:
1. **Status Line:**
   * *Protocol Version:* The HTTP version implemented by the server (e.g., `HTTP/1.1`).
   * *Status Code:* A 3-digit numeric indicator of the transaction's outcome (e.g., `201`).
   * *Status Reason Phrase:* A human-readable text explanation (e.g., `Created`).
2. **Response Headers:** Metadata describing the server environment, caching instructions, and payload attributes.
3. **Blank Line:** CRLF (`\r\n`) delimiter separating headers from the payload.
4. **Response Payload / Body:** The returned data representation.

```http
HTTP/1.1 201 Created
Date: Mon, 02 Nov 2026 18:00:00 GMT
Content-Type: application/json
Content-Length: 42

{"id": 101, "status": "user_initialized"}
```

## 4. Deep Dive into HTTP Headers

### Why Headers Exist (The Courier Parcel Analogy)
Why create an isolated abstraction layer for headers instead of embedding all metadata directly inside the URL or the request body?
* *The Analogy:* When shipping a physical package via a courier service, shipping instructions, recipient names, street addresses, postal codes, and handling warnings are written on an **external label stuck to the outside of the box**, not sealed inside it.
* *The Engineering Reason:* Network intermediaries (reverse proxies, load balancers, API gateways, CDNs, firewalls) need to inspect routing, authentication, and content constraints rapidly. If metadata were buried inside the body, every intermediate node would be forced to allocate memory, buffer the stream, and fully parse the body at every network hop. Headers allow fast, zero-overhead inspection.

### The Four Primary Header Categories

```
                    ┌─────────────────────────────────────┐
                    │         HTTP Header Types           │
                    └──────────────────┬──────────────────┘
         ┌──────────────────┬──────────┴──────────┬──────────────────┐
         ▼                  ▼                     ▼                  ▼
  Request Headers    General Headers    Representation Headers Security Headers
(Client environment,  (Transport/state,   (Payload encoding,   (Browser defense,
  auth, capabilities)  caching metadata)    size, MIME type)    XSS/framing/SOP)
```

1. **Request Headers:** Convey the client's execution environment, hardware capabilities, and credentials:
   * `User-Agent`: Identifies the client software (e.g., Chrome, Postman, cURL, Python `requests`).
   * `Authorization`: Transmits client authentication credentials (e.g., `Bearer <token>`, `Basic <base64>`).
   * `Accept`: Informs the server of the MIME formats the client can parse (`application/json`, `text/html`).
2. **General Headers:** Contextual properties that apply to the overarching message lifecycle independent of payload content:
   * `Date`: The exact UTC timestamp when the message was originated.
   * `Cache-Control`: Primary directive governing intermediate and client cache behavior (`no-cache`, `max-age=3600`).
   * `Connection`: Controls transport persistence (`keep-alive`, `close`).
3. **Representation Headers:** Describe the specific format, dimensions, and encoding applied to the message body:
   * `Content-Type`: The media/MIME type of the payload (`application/json`, `text/plain`, `multipart/form-data`).
   * `Content-Length`: The exact size of the payload body calculated in bytes.
   * `Content-Encoding`: Compression algorithms applied to the payload over the wire (`gzip`, `br`, `deflate`).
   * `ETag`: An opaque entity hash representing the specific version of the resource representation.
4. **Security Headers:** Mandate strict defensive execution rules inside the client browser:
   * `Strict-Transport-Security` (HSTS): Instructs browsers that the domain must exclusively be accessed over HTTPS, preventing SSL-stripping and protocol-downgrade attacks.
   * `Content-Security-Policy` (CSP): Enforces a strict whitelist of trusted origins from which scripts, stylesheets, and images can execute, mitigating Cross-Site Scripting (XSS).
   * `X-Frame-Options`: Restricts whether a page can be rendered inside `<frame>`, `<iframe>`, or `<object>` tags, neutralizing clickjacking.
   * `X-Content-Type-Options: nosniff`: Prevents browsers from guessing (sniffing) a MIME type different from the declared `Content-Type`.
   * `Set-Cookie`: Transmits state cookies with defensive flags:
     * `HttpOnly`: Blocks client-side JavaScript (`document.cookie`) from reading the cookie, mitigating credential theft via XSS.
     * `Secure`: Restricts cookie transmission strictly to encrypted HTTPS channels.
     * `SameSite=Strict|Lax`: Protects against Cross-Site Request Forgery (CSRF).

### Architectural Philosophy of Headers
* **Extensibility:** The protocol does not require redesigns when new features emerge. Engineers can introduce novel behaviors simply by defining new standardized or proprietary headers (e.g., `X-Request-ID` for distributed tracing).
* **Remote Control:** Headers act as a bi-directional remote control mechanism. Clients configure server execution rules (via `Accept`, `Prefer`), and servers dictate client behaviors (via `Cache-Control`, `Set-Cookie`, `Location`).

## 5. HTTP Methods & Idempotency

### Semantic Intent of Methods
HTTP methods are verbs that define the **semantic intent** of an operation on a target resource:
* `GET`: Fetches a resource representation. Must remain strictly read-only with zero server-side state mutations.
* `POST`: Submits a representation to append, process, or create a subordinate entity. Contains a request body.
* `PATCH`: Applies **partial modifications** to an existing resource. The body specifies only the delta/subset of fields to alter.
* `PUT`: Completely **replaces** the target resource with the submitted payload. If fields are omitted in the PUT body, the server typically overwrites them with null or defaults.
  * *Golden Rule:* Modern APIs often default to `PATCH` for updates. Reserve `PUT` strictly for cases where full resource replacement is intended.
* `DELETE`: Removes the designated resource from the system.
* `OPTIONS`: Queries the server's capabilities and allowed communication methods without executing business actions. Forms the backbone of CORS preflight checks.

### The Concept of Idempotency
An operation is mathematically **idempotent** if invoking it $N$ times sequentially produces the identical system state as invoking it exactly once:

$$
f(f(x)) = f(x)
$$

```
              ┌──────────────────────────────────────────┐
              │           HTTP Method Taxonomy           │
              └────────────────────┬─────────────────────┘
                     ┌─────────────┴─────────────┐
                     ▼                           ▼
            Idempotent Methods           Non-Idempotent Methods
        [GET, PUT, DELETE, OPTIONS]              [POST]
    Multiple identical calls yield the      Repeated calls cause new,
      same resulting server state.         cumulative server side-effects.
```

* **Idempotent Methods:**
  * `GET`: Fetching a record 1 time or 10,000 times does not mutate server state.
  * `PUT`: Overwriting a record with payload $X$ multiple times leaves the record in state $X$ every time.
  * `DELETE`: Deleting record `ID=5` removes it. Calling `DELETE` 10 more times does not delete additional records; the resource remains deleted (even if subsequent calls return `404 Not Found`, the server state is unchanged).
* **Non-Idempotent Methods:**
  * `POST`: Executing `POST /api/orders` once creates 1 order. Executing the exact same request 5 times creates **5 distinct order entries** with 5 unique primary keys. Every invocation triggers cumulative side-effects.

## 6. Same-Origin Policy & CORS (Cross-Origin Resource Sharing)

### Same-Origin Policy (SOP)
The browser implements the **Same-Origin Policy** as a fundamental security boundary. SOP dictates that a script running on one origin cannot read sensitive data from a different origin. An origin is defined strictly by the tuple:

$$\text{Origin} = (\text{Protocol}, \text{Domain}, \text{Port})$$

* *Example:* If your single-page app runs on `http://localhost:5173` and requests data from an API at `http://localhost:3000`, the ports differ. This is classified as a **cross-origin request**.
* **CORS (Cross-Origin Resource Sharing):** The standardized HTTP-header mechanism that allows a server to explicitly inform the browser which external origins are authorized to read its responses.

---

### Flow 1: Simple Request Flow
A cross-origin request is classified as **Simple** only when it satisfies all of the following:
1. Uses a simple method: `GET`, `POST`, or `HEAD`.
2. Includes only simple, automated headers (`Accept`, `Accept-Language`, `Content-Language`).
3. Uses a simple `Content-Type`: `application/x-www-form-urlencoded`, `multipart/form-data`, or `text/plain`.

```
Client (http://localhost:5173)                   Server (http://localhost:3000)
       │                                                       │
       │─── 1. GET /api/data ─────────────────────────────────>│
       │    Origin: http://localhost:5173                      │
       │                                                       │
       │<── 2. HTTP 200 OK ────────────────────────────────────│
       │    Access-Control-Allow-Origin: http://localhost:5173 │
       │    [Response Body]                                    │
       │                                                       │
[Browser validates header; passes data to JS]
```

* **The Browser-Interception Mechanism:** If the server processes a simple request but fails to attach `Access-Control-Allow-Origin: http://localhost:5173` (or `*`), **the request still executes on the server**. The server generates and returns the data, but the **browser intercepts the response**, refuses to expose the payload to client JavaScript, and logs a `CORS Error` in the developer console.

---

### Flow 2: Preflighted Request Flow
If a cross-origin request triggers **any one** of the following conditions, the browser must issue an automated **Preflight Request** before the actual request can fire:
1. Uses a non-simple method (`PUT`, `DELETE`, `PATCH`).
2. Attaches non-simple headers (e.g., `Authorization`, `X-Custom-Header`).
3. Sets a non-simple `Content-Type` (most notably `application/json`).

> *Critical Note:* Because virtually all modern web and mobile applications communicate using `Content-Type: application/json` and bearer authorization headers, **nearly all modern cross-origin API calls trigger preflights**.

```
Client (http://localhost:5173)                   Server (http://localhost:3000)
       │                                                       │
       │─── 1. OPTIONS /api/resource ─────────────────────────>│
       │    Origin: http://localhost:5173                      │
       │    Access-Control-Request-Method: PUT                 │
       │    Access-Control-Request-Headers: authorization, ... │
       │                                                       │
       │<── 2. HTTP 204 No Content ────────────────────────────│
       │    Access-Control-Allow-Origin: http://localhost:5173 │
       │    Access-Control-Allow-Methods: GET, POST, PUT, ...  │
       │    Access-Control-Allow-Headers: Authorization, ...   │
       │    Access-Control-Max-Age: 86400                      │
       │                                                       │
[Browser checks allowances; dispatches actual payload]         │
       │                                                       │
       │─── 3. PUT /api/resource ─────────────────────────────>│
       │    Authorization: Bearer <token>                      │
       │    Content-Type: application/json                     │
       │    {"key": "value"}                                   │
       │                                                       │
       │<── 4. HTTP 200 OK ────────────────────────────────────│
       │    Access-Control-Allow-Origin: http://localhost:5173 │
       │    {"status": "updated"}                              │
```

#### Anatomy of Preflight Headers
* `Access-Control-Request-Method`: The client asking: *"Will you allow me to use `PUT` on this URL?"*
* `Access-Control-Request-Headers`: The client asking: *"Will you allow me to send the `authorization` and `content-type` headers?"*
* `Access-Control-Allow-Origin`: The server granting access to specific origins or all origins (`*`).
* `Access-Control-Allow-Methods`: A comma-separated list of permitted HTTP methods.
* `Access-Control-Allow-Headers`: A comma-separated list of permitted request headers.
* `Access-Control-Max-Age`: Cache TTL (in seconds) for the preflight permission, preventing redundant preflight roundtrips on subsequent requests.

## 7. Comprehensive HTTP Status Codes Reference

Status codes provide a language-agnostic contract between clients and servers. They inform client logic how to handle an outcome without requiring body inspection.

### 1xx: Informational
* `100 Continue`: Sent by the server to indicate that initial request headers have been accepted and the client may proceed to transmit the (often large) request body.
* `101 Switching Protocols`: Sent when the server agrees to upgrade the connection protocol (e.g., upgrading an HTTP connection to a full-duplex **WebSocket** connection).

### 2xx: Success
* `200 OK`: Standard success response for reads (`GET`) or updates (`PUT`/`PATCH`).
* `201 Created`: The request succeeded and led to the creation of a brand-new resource instance (standard for `POST` actions). The response typically includes a `Location` header or the new entity payload.
* `204 No Content`: The action was successfully executed, but there is intentionally no payload body to return (used for CORS `OPTIONS` preflight responses and `DELETE` calls).

### 3xx: Redirection
* `301 Moved Permanently`: The requested URL has been assigned a permanent new URI. Search engine crawlers update their indices, and clients automatically update bookmarks.
* `302 Found (Temporary Redirect)`: The resource resides temporarily at an alternate URI. Future requests should still use the original URI.
* `304 Not Modified`: Directs the client to use its locally cached copy of the resource because the data has not changed since the client's last conditional request. Contains no body.

### 4xx: Client Errors
* `400 Bad Request`: The payload contains malformed syntax, failed field validations, or illogical types (e.g., passing a string where an integer is expected).
* `401 Unauthorized`: Semantically means **Unauthenticated**. The client has either provided invalid credentials or omitted the required authorization token entirely.
* `403 Forbidden`: The client **is authenticated**, but lacks sufficient authorization/permissions to access the target entity (e.g., an ordinary user trying to delete an admin record).
* `404 Not Found`: The target URI path does not exist on the server, or the specific resource record has been deleted.
* `405 Method Not Allowed`: The resource exists, but does not support the HTTP verb used (e.g., firing a `PUT` request against an endpoint that only implements `GET`).
* `409 Conflict`: The request cannot be completed due to a conflict with current server state (e.g., attempting to register a unique username or folder name that already exists).
* `429 Too Many Requests`: The client has exceeded the server's rate-limiting policy (e.g., firing more than 60 requests per minute). Typically paired with a `Retry-After` header.

### 5xx: Server Errors
* `500 Internal Server Error`: An unhandled exception, syntax failure, or crash occurred within server-side code. For security, never expose internal stack traces in production 500 responses.
* `501 Not Implemented`: The server does not support the functionality required to satisfy the request.
* `502 Bad Gateway`: Returned by reverse proxies (e.g., NGINX, Cloudflare) when the upstream application server process returns an invalid, garbled, or unreadable response.
* `503 Service Unavailable`: The server is currently unable to handle requests due to high-traffic exhaustion or active scheduled maintenance.
* `504 Gateway Timeout`: Returned by reverse proxies or edge gateways when an upstream application service fails to complete its processing and reply within a configured timeout window.

## 8. HTTP Caching & Conditional Requests Lifecycle

Caching prevents redundant data transmission, reduces latency, and protects primary databases from load spikes.

### The Caching Lifecycle: Step-by-Step

```
Client / Browser                                           Backend Server
       │                                                         │
       │─── 1. Initial Request: GET /api/resource ──────────────>│
       │                                                         │
       │<── 2. Response: 200 OK ─────────────────────────────────│
       │       Cache-Control: max-age=10                         │
       │       ETag: "3141"                                      │
       │       Last-Modified: Mon, 02 Nov 2026 12:00:00 GMT      │
       │       [Payload Body]                                    │
       │                                                         │
[Client caches payload, ETag "3141", and timestamp]              │
[Wait 10 seconds (cache becomes stale)...]                       │
       │                                                         │
       │─── 3. Conditional Request: GET /api/resource ──────────>│
       │       If-None-Match: "3141"                             │
       │       If-Modified-Since: Mon, 02 Nov 2026 12:00:00 GMT  │
       │                                                         │
       │       [Server evaluates: Resource NOT modified]         │
       │                                                         │
       │<── 4. Cache Hit: 304 Not Modified ──────────────────────│
       │       (No Body Transmitted over the wire)               │
       │                                                         │
[Browser renders local cached copy immediately]                  │
       │                                                         │
[Resource updated on server -> Server generates ETag "2943"]     │
       │                                                         │
       │─── 5. Subsequent Request: GET /api/resource ───────────>│
       │       If-None-Match: "3141"                             │
       │                                                         │
       │       [Server evaluates: "3141" != "2943" (Dirty)]      │
       │                                                         │
       │<── 6. Cache Miss / Invalidation: 200 OK ────────────────│
       │       ETag: "2943"                                      │
       │       [Fresh Updated Body Payload]                      │
```

1. **The Initial Request:** The browser requests a resource for the first time. The server returns `200 OK` accompanied by three foundational caching headers:
   * `Cache-Control: max-age=10`: Declares the cached resource fresh for 10 seconds.
   * `ETag: "3141"`: A cryptographic fingerprint/hash representing the body representation.
   * `Last-Modified: <timestamp>`: The date and time the entity was last edited.
2. **Conditional Validation (`If-None-Match`):** Once `max-age` expires, the client makes a conditional request attaching `If-None-Match: "3141"`.
3. **The `304 Not Modified` Response:** The server hashes the current resource. If the hash matches `"3141"`, the server returns a `304 Not Modified` with an empty body, saving bandwidth.
4. **Cache Invalidation:** If the resource undergoes a write operation, the server recomputes the ETag (e.g., `"2943"`). When the client calls `If-None-Match: "3141"`, the mismatch causes the server to return `200 OK`, the new ETag, and the full updated payload.

## 9. Content Negotiation & Compression

Content Negotiation allows clients and servers to dynamically agree on data representations without changing resource paths.

```
       Client Headers Sent                              Server Evaluation & Response
┌─────────────────────────────────┐                 ┌─────────────────────────────────┐
│ Accept: application/json        │ ──────────────> │ Content-Type: application/json  │
│ Accept-Language: es             │                 │ Content-Language: es            │
│ Accept-Encoding: gzip, br       │                 │ Content-Encoding: gzip          │
└─────────────────────────────────┘                 └─────────────────────────────────┘
```

1. **Media Type Negotiation:** Driven by the client's `Accept` header (e.g., `application/json` vs. `application/xml`).
2. **Language Negotiation:** Driven by `Accept-Language` (e.g., `es` vs. `en`). The server serves localized string responses based on this preference.
3. **Encoding & Compression:**
   * The client advertises supported decompression algorithms using `Accept-Encoding: gzip, deflate, br`.
   * The server compresses the response body, sets `Content-Encoding: gzip`, and sends the compressed byte stream over the network.
* **Production Impact of Compression:**
  * Serving an uncompressed JSON file of 11,000 records requires **~26 MB** of bandwidth.
  * Applying standard `gzip` compression reduces the network transfer payload to **~3.8 MB** (an ~85% reduction in data transfer), vastly improving loading speeds.

## 10. Persistent Connections & Keep-Alive

### The HTTP/1.0 Connection Bottleneck
In early HTTP/1.0, every single request required creating a new TCP connection (3-way handshake) and terminating it immediately after the response was sent. For pages loading dozens of assets, this created immense latency and wasted server CPU and memory.

### Persistent Connections in HTTP/1.1
* In HTTP/1.1, connections are **persistent by default**. A single TCP socket connection remains open to process multiple sequential requests and responses.
* `Connection: keep-alive`: Explicitly maintains the socket connection. Can be paired with parameters:
  * `timeout=5`: The duration (in seconds) the server keeps an idle connection open.
  * `max=1000`: The maximum number of requests allowed over the connection before it is closed.
* `Connection: close`: Forces the server to terminate the underlying TCP connection immediately after transmitting the response body.

## 11. Handling Large Payloads: Multipart & Streaming

### 1. Uploading Large Files (`multipart/form-data`)
Standard JSON is ill-suited for large binary files (images, videos, documents). File uploads utilize multipart encoding:
* **The `boundary` Delimiter:** The header sets `Content-Type: multipart/form-data; boundary=----WebKitFormBoundary...`.
* The boundary string serves as a delimiter separating different files, fields, and raw binary chunks in the request stream, allowing the server to parse distinct fields without buffering the entire file into memory first.

### 2. Streaming Responses (Chunked Transfer & SSE)
Instead of buffering an entire massive response into RAM before transmitting it, the server can stream data incrementally in chunks as it is generated:
* `Content-Type: text/event-stream`: Used for streaming text data via **Server-Sent Events (SSE)**.
* `Connection: keep-alive`: Retains the underlying transport channel open indefinitely while data chunks are continuously piped down to the client.

## 12. SSL, TLS, and HTTPS

### The Cryptographic Security Layer
```
┌────────────────────────────────────────────────────────┐
│           Layer 7: HTTP Application Data               │
├────────────────────────────────────────────────────────┤
│           TLS Encryption Layer (TLS 1.3)               │
│  - Symmetric encryption (Confidentiality)              │
│  - Digital certificates & asymmetric handshake (Auth)  │
│  - Cryptographic hashes (Integrity)                    │
├────────────────────────────────────────────────────────┤
│           Layer 4: TCP Transport Layer                 │
└────────────────────────────────────────────────────────┘
```

* **SSL (Secure Sockets Layer):** The original encryption protocol designed to secure client-server traffic. **SSL is now deprecated** due to critical vulnerabilities (e.g., POODLE, Heartbleed).
* **TLS (Transport Layer Security):** The modern, secure successor to SSL.
  * Encrypts data in transit to prevent eavesdropping and interception of sensitive credentials.
  * Uses **Digital Certificates** issued by Certificate Authorities (CAs) to authenticate the true identity of the server, preventing Man-in-the-Middle (MitM) attacks.
  * Ensures data integrity by verifying that packets have not been tampered with in transit.
  * **TLS 1.3** is the current industry standard, featuring a faster 1-RTT handshake and enhanced cipher suites.
* **HTTPS (HTTP Secure):** Standard HTTP running over a TLS-encrypted tunnel. At the application layer, backend request routing, headers, and status codes remain unchanged; the transport bytes are simply encrypted before transmission and decrypted upon arrival.
